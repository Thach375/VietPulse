# M2.3 · speed-sentiment bản đầu

Query A đọc Kafka bằng Spark Structured Streaming 4.0.4 (được nâng từ 3.5.3 ở Task 6), kiểm envelope, chuẩn hóa và chấm sentiment bằng luật trong `common/text_processing.py`, rồi ghi Elasticsearch qua Bulk API. Một micro-batch mặc định chạy mỗi 30 giây, lấy tối đa 10.000 offset.

Luồng hiện có:

```text
raw.news.articles ─┐                    ┌─ hợp lệ → sentiment → vp-docs
raw.news.comments ├─ query A, checkpoint┤
raw.forum.posts ──┘                    └─ lỗi → vp-dlq (Elasticsearch) + dlq.raw (Kafka)
```

Query A không giữ state giữa các batch và không áp watermark. Bản ghi cũ hơn 6 giờ vẫn vào `vp-docs`. Task 6 bổ sung nhánh tổng hợp qua `--enable-windows`: khử trùng và tổng hợp dùng hai query với checkpoint riêng, watermark 6 giờ, cửa sổ cố định 5 phút và MongoDB `rt_window`. HDFS chứa dữ liệu trung gian vì Spark 4 không cho nối hai bước có state ở Update mode; xem [runbook Task 6](../infra/docs/processing-runbook.md). `raw.backfill` chỉ dành cho raw-ingest. Nguồn YouTube chỉ được đọc khi thêm `raw.youtube.comments` vào `--topics` và tạo topic trước.

`alerts.sentiment` đã có topic nhưng chưa có đặc tả luật/ngưỡng cảnh báo, nên M2.3 chưa phát cảnh báo nghiệp vụ. PhoBERT thuộc M4.2; dashboard Kibana thuộc M2.4.

## Chạy trên Compose

Tại thư mục repo, cần Docker đang chạy:

```bash
docker compose up -d --build spark kafka-init
docker compose ps -a
docker compose exec spark python -m jobs.setup_elasticsearch --url http://elasticsearch:9200
docker compose exec spark spark-submit jobs/speed_sentiment.py
```

Chờ Kafka, Elasticsearch healthy và kafka-init thoát mã 0 trước khi submit. Connector đã khai báo trong `docker/spark-dev/spark-defaults.conf`. Không cần cài thêm thư viện Python cho job trong container.

Chỉ xử lý backlog hiện có rồi thoát:

```bash
docker compose exec spark spark-submit jobs/speed_sentiment.py --available-now
```

Chạy lại cùng lệnh sẽ tiếp tục từ checkpoint `data/checkpoints/speed-sentiment-documents`. `startingOffsets` chỉ áp dụng khi chưa có checkpoint. Không dùng chung checkpoint giữa các query, không chạy hai instance cùng checkpoint; giữ checkpoint trên storage bền vững khi đưa lên k3s. Kafka mất offset do hết retention hoặc bị tạo lại thì job báo lỗi, thay vì bỏ qua dữ liệu.

Các tham số chạy xem bằng `spark-submit jobs/speed_sentiment.py --help`: broker, topics, checkpoint, trigger, giới hạn offset, URL Elasticsearch và tên index đều cấu hình được. URL mặc định là địa chỉ nội bộ Compose; chạy từ host cần đổi broker thành `localhost:9094` và Elasticsearch thành `http://localhost:9200`.

## Tài liệu Elasticsearch và hợp đồng cần review

Mapping nằm trong `jobs/setup_elasticsearch.py`; script tạo mới hoặc cập nhật mapping, không xóa index đã có. Mapping xung đột sẽ báo lỗi. Query A tự kiểm tra mapping khi khởi động. Compose dùng HTTP không xác thực; trên K3s, `VP_ES_PASSWORD_FILE` và `VP_ES_CA_FILE` trỏ đến Secret được mount, và URL phải là HTTPS. Task 6 dùng Bulk API với kiểm tra lỗi từng item.

`vp-docs` là index lâu dài. `_id` = `source:record_id`, cùng quy ước khóa Kafka trong `common/envelope.py`, vì id bài báo và bình luận cùng trang có thể trùng. Batch-publish cần dùng cùng khóa này.

| Trường | Kiểu Elasticsearch | Ý nghĩa |
| --- | --- | --- |
| document_id, source, record_id | keyword | định danh, nguồn |
| event_time, ingest_time | date | UTC; dùng event_time làm time field trong Kibana |
| schema_version | long | phiên bản envelope gốc |
| site, category, article_id, thread_id | keyword | lọc, nhóm và liên kết nguồn |
| title, summary, body, content, thread_title, normalized_text | text | tìm kiếm toàn văn; nội dung rỗng được chấm neutral |
| payload_json | text, không index | toàn bộ payload gốc, giữ cả trường bổ sung và cấu trúc lồng nhau |
| url | keyword, không index | đường dẫn nguồn |
| sentiment.label, sentiment.model | keyword | positive/negative/neutral; model = rules-v1 |
| sentiment.score | double | điểm luật có dấu, không phải xác suất và không bị chặn trong [-1, 1] |

Trong mỗi micro-batch, các bản cùng khóa được chọn theo ingest_time mới nhất; hòa thì theo Kafka timestamp, partition, offset. Connector ghi `index` theo `_id` cố định: tạo nếu chưa có, thay toàn bộ tài liệu nếu đã có. Đây là upsert theo định danh; không dùng Elasticsearch partial update. Thứ tự giữa các batch theo checkpoint; không có cơ chế chống một bản crawl cũ được gửi lại ở batch sau ghi đè bản mới.

`vp-dlq` là **alias đọc** của các index `vp-dlq-yyyy.MM.dd` theo ngày UTC của Kafka timestamp. Mỗi index có policy ILM xóa sau 3 ngày kể từ lúc tạo index (không phải TTL từng tài liệu); alias được giữ qua template. Không tạo index vật lý tên `vp-dlq`. `_id` lỗi = `source_topic:partition:offset`, ổn định qua retry/replay. Ngày Kafka được dùng để retry sang ngày khác vẫn ghi cùng index; replay dữ liệu đã bị ILM xóa có thể tạo lại index đó.

DLQ giữ `raw_value`, `error`, `source_topic`, `partition`, `offset`, `kafka_timestamp`, `detected_at`. `raw_value` được giữ cả khi Kafka value là null; chỉ index Elasticsearch có thêm `document_id`. Luật tách lỗi gồm JSON hỏng/không phải object, thiếu trường envelope, source sai hoặc không khớp topic, record_id rỗng/sai kiểu, schema_version không phải số nguyên dương, payload không phải object, timestamp không hợp lệ/không phải UTC kết thúc bằng Z và event_time ở tương lai quá 1 giờ.

Envelope và Kafka topics không đổi. Cấu trúc tài liệu, khóa index và alias DLQ là phần hợp đồng serving mới của M2.3; cần Quang, Đạt (batch-publish) thống nhất và Thái review trước khi merge theo CONTRIBUTING.md.

## Ghi lỗi và khôi phục

Job cache dữ liệu đã parse trong từng batch, ghi tài liệu tốt vào `vp-docs`, ghi lỗi vào Elasticsearch rồi Kafka. Chỉ khi các sink đều thành công Spark mới commit batch. Sink lỗi sẽ làm query dừng và giải phóng cache; chạy lại cùng checkpoint để Spark thử lại. Log ứng dụng ghi batch id và số bản ghi tốt/lỗi.

Elasticsearch được ghi idempotent theo `_id`. Kafka DLQ là **at-least-once**: có thể lặp nếu Kafka đã nhận nhưng batch chưa commit, hoặc chủ động replay bằng checkpoint mới. Key DLQ ổn định để đối soát. Không có transaction chung giữa Kafka và Elasticsearch; không coi toàn bộ luồng là exactly-once.

## Kiểm thử

Unit test gồm Spark local, bật ANSI để kiểm timestamp hỏng không làm job chết. Chạy ngoài container cần Python 3.11 và Java 17 trong PATH. CI cài cùng phiên bản và extra `streaming` để chạy phần này:

```bash
pip install -e ".[crawler,streaming,dev]"
pytest -q
ruff check .
ruff format --check .
```

Nếu chỉ cài `crawler,dev`, test Spark được skip. Có thể chạy toàn bộ test trong container dev sau khi cài test dependencies:

```bash
docker compose exec spark pip install -e ".[crawler,dev]"
docker compose exec -e SPARK_CONF_DIR=/tmp spark python -m pytest -q
```

Integration smoke test tự tạo dữ liệu tổng hợp vào ba topic raw, dùng index/policy/template/checkpoint có tiền tố ngẫu nhiên, kiểm cả sink thật, resume, replay, cập nhật và cấu hình ILM:

```bash
docker compose exec spark spark-submit --master local[2] tests/integration/speed_sentiment_smoke.py
```

Kết quả mong đợi: `M2.3 OK (...): 4 tài liệu, 4 DLQ; resume, replay, cập nhật và ILM đều đúng`. Test không xóa dữ liệu có sẵn; các tài nguyên thử còn lại để kiểm tra. Chạy trên Compose dev vì test gửi bản ghi lỗi tổng hợp vào topic raw dùng chung; không chạy khi đang đo dữ liệu thật. Kiểm thử này chưa thay thế kiểm thử chịu lỗi trên k3s ở M5.1.

Tài liệu tham chiếu: [Spark Structured Streaming](https://spark.apache.org/docs/3.5.7/structured-streaming-programming-guide.html), [Kafka source/sink](https://spark.apache.org/docs/3.5.7/structured-streaming-kafka-integration.html), [Elasticsearch Hadoop options](https://www.elastic.co/guide/en/elasticsearch/hadoop/8.15/configuration.html), [ILM](https://www.elastic.co/guide/en/elasticsearch/reference/8.15/index-lifecycle-management.html). Hai link Spark thuộc cùng dòng 3.5; phiên bản chạy được pin 3.5.3 và được kiểm tra trên Compose.
